# ADR-0009 — Multi-Agent Consultation Architecture and Controlled Autonomy

**Status:** Accepted — Product/Architecture Direction  
**Date:** 2026-11-03  
**Scope:** Kunkor grades 10–12 (high school) Autonomous Educational Consultant  
**Decision owners:** Product Owner / Technical Lead  
**Related ADRs:** ADR-0001 through ADR-0008  
**Supersedes:** Previous single bounded-consultant assumption in D-10 (once decision register is updated)

---

## 1. Context

Kunkor must provide autonomous, personalized educational consultation for grades 10–12 (high school) students. The system must collect and maintain student context, understand educational resources, generate feasible study plans, monitor daily execution, and revise plans based on actual progress.

The product must support multiple consultant agents with distinct consultation strategies. A Supervisor evaluates their proposals and selects or combines the best result.

The content catalog is built from scratch. The system must never fabricate book structures, page counts, question counts, difficulty labels, or resource coverage.

**D-13 clarification (2026-11-05):** "From scratch" means an initially empty, functional owner-managed catalog. Phase 2 is accepted with zero real educational records and automated synthetic fixtures only. Manual owner entry is continuous operation after deployment. Draft resources and individual chapters/lessons/sections/topics can be saved and extended incrementally; valid units publish independently of parent/catalog completeness. Trusted use requires explicit owner approval, publication, and active rights. Missing resources return empty results or an awaiting-content state and do not block unrelated capabilities. The [mandatory content contract](../PHASE_2_EMPTY_TO_GROW.md) governs these requirements.

## 2. Decision

Kunkor adopts a **Multi-Agent-First, Backend-Controlled Autonomous Consultation Architecture**.

The architecture is implemented inside the existing modular monolith. It does not introduce microservices as a prerequisite.

### 2.1 Agent architecture

The initial system includes:

1. **Intake Agent** — adaptive student interview and missing-information detection
2. **Student Modeling Agent** — structured educational profile and learning-context analysis
3. **Content Intelligence Agent** — retrieval of approved books, chapters, lessons, pages, and questions
4. **Planning Consultant Agents** — multiple independent consultation strategies
5. **Progress Agent** — daily execution analysis and identification of deviations
6. **Revision Agent** — evidence-based plan revision
7. **Supervisor/Evaluator** — proposal comparison, conflict resolution, quality scoring, and final selection

Agents communicate through versioned, typed contracts. The Orchestrator controls execution order, parallelism, retries, budgets, and timeouts.

Not every user request must invoke all agents. The Orchestrator selects the necessary agents based on the request type.

### 2.2 Authority and write permissions

- Agents may reason, retrieve approved data, and generate structured proposals.
- Agents **cannot** directly write to PostgreSQL.
- The Supervisor may select or combine proposals but **cannot** bypass domain validation.
- Domain services own all persistent changes.
- The deterministic validation engine enforces hard constraints before a plan or revision is activated.
- Every consequential decision records: responsible agent, model/provider, prompt/configuration version, input context version, proposal, validation result, and final action.

### 2.3 Full autonomy

Routine consultation, plan activation, daily monitoring, and plan revision are automatic.

The student does not need to approve ordinary plan updates. The system must notify the student of material changes and explain their reasons.

The system must stop or enter a safe degraded state when:

- required educational evidence is unavailable;
- the student context is materially incomplete or contradictory;
- candidate plans violate hard constraints;
- the Supervisor cannot resolve a material disagreement;
- backend authorization, provider disablement, credential, budget or validation controls cannot be satisfied.

No unsupported plan may be activated merely to preserve the appearance of autonomy.

### 2.4 Content intelligence

The content system is developed from scratch with a versioned hierarchy:

```
Curriculum → Subject → Book → Edition → Chapter → Lesson → Section/Page → Question
```

It must support:

- source and edition provenance
- license and usage rights
- exact page and question counts where verified
- question difficulty and estimated completion time where supported
- curriculum and learning-objective mapping
- prerequisites and topic relationships
- content versioning, review, publication, expiry, and correction
- explicit `no_source` and `unknown` states

Content ingestion and publication are separate processes. Unreviewed material cannot be treated as authoritative. The LLM is **not** the source of truth for page counts or question counts.

### 2.5 Planning authority

AI agents generate candidate plans. A deterministic planning and validation layer checks:

- available daily and weekly time
- exam and school deadlines
- resource availability
- prerequisite ordering
- estimated task duration
- daily workload limits
- unfinished work and historical progress
- consistency with the student's current profile

Only a validated plan can be activated.

### 2.6 Persistence and execution

Conversation turns, agent runs, proposals, decisions, plan versions, task executions, and progress evidence must be durable and recoverable.

Operations must be idempotent where retries or duplicate Telegram messages can occur. Plan changes are versioned; prior versions are retained as historical evidence.

### 2.7 Evaluation

Each consultant agent and the Supervisor must have independent evaluation cases covering:

- educational relevance and feasibility
- content grounding and provenance
- Persian conversational quality
- consistency across repeated runs
- student-context isolation
- resistance to prompt injection and untrusted content
- latency, token use, provider failure, and cost
- quality of daily revisions

A Supervisor is not considered reliable merely because it agrees with another model. It must demonstrate measurable selection quality against reviewed evaluation cases.

## 3. Alternatives considered

| Alternative | Decision |
|-------------|----------|
| Single consultant only | Rejected as target architecture |
| Independent agents with unrestricted tool access | Rejected — uncontrolled writes and security risk |
| Microservices for every agent | Rejected initially — unjustified operational complexity |
| LLM-only planning without deterministic validation | Rejected — cannot guarantee feasibility or factual content counts |
| Fully sequential execution of every agent | Rejected as universal strategy — unnecessary cost/latency |
| Supervisor with unrestricted database authority | Rejected — violates single write authority |

## 4. Consequences

**Positive**
- Multi-agent behavior is a first-class architecture capability
- Consultant strategies can evolve independently and be compared
- Full autonomy is possible without granting agents unrestricted authority
- Content, planning, progress, and revision share consistent contracts
- Agent quality can be measured and improved over time

**Costs and risks**
- More complex orchestration, evaluation, observability, and version management
- Higher inference cost and latency when multiple agents are invoked
- Risk of correlated model errors and false confidence from the Supervisor
- Additional effort to create and verify the educational content catalog

**Mitigations**
- Conditional agent routing and bounded parallelism
- Per-turn and per-student model budgets
- Typed outputs, deterministic validation, and explicit no-source behavior
- Versioned evaluation suites and human educational review of the benchmark
- Central backend authorization and domain-owned writes

## 5. Implementation constraints

- Preserve ADR-0001 modular monolith
- Preserve ADR-0002 technology stack unless a separately approved decision changes it
- Interpret ADR-0003 as mandatory for all agent-triggered actions
- **Amend ADR-0004** to distinguish AI educational reasoning and candidate generation from deterministic hard-constraint validation
- **Amend ADR-0005** to retain versioned decisions and progress evidence while implementing privacy-compliant retention and erasure
- **Amend ADR-0006**: AI is a core runtime dependency for full consultation; provider abstraction and degraded mode remain mandatory
- Preserve ADR-0007 structured retrieval first
- Preserve ADR-0008 student-level isolation on all student-owned records

## 6. Framework decision

The architecture is framework-independent. The orchestration implementation must be selected through a bounded technical spike comparing durable execution, state recovery, parallel agents, typed contracts, tracing, provider flexibility, testability, and cost.

The framework must not own domain data or bypass Kunkor's backend authorization and persistence services.

## 7. Acceptance criteria

ADR-0009 is implemented when:

1. Multiple consultant agents can independently produce typed proposals
2. The Supervisor can compare proposals and produce a traceable selection
3. Agent execution is bounded by explicit time, token, and cost limits
4. No agent can directly persist student or plan changes
5. A deterministic validator rejects infeasible plans
6. Conversation and agent execution can recover after interruption
7. Every decision is attributable to versions of inputs, agents, prompts, and validators
8. Evaluation cases demonstrate acceptable grounding, feasibility, privacy, and revision quality
